# UI 教训记录

被用户纠正过的界面问题都记在这里。**记的重点是用户的意图和我思路上的错，不是表面的那个 bug**：一个功能只会做一次，同样的意图、同样的思路错误却会在别的功能上再犯。具体的错只作为例子。

**怎么写一条教训**（用户 2026-11-26 要求）
1. **用户的意图**：用户真正想要什么，用一句适用于所有界面的话说出来，不提具体功能。
2. **我的思路错在哪**：我当时是怎么想的、为什么会这样想。要能在别的功能上认出同一种想法。
3. **这次的表现**：具体是哪个功能、哪里错了（例子，可以有好几个）。
4. **以后**：做任何界面时都要遵守的做法，不限于这个功能。
5. **自动检查**：能程序化的写成检查（`scripts/ui-check.py` 的 C、`scripts/ui-shot-check.py` 的 S），并在仓库副本里故意造一次这个错，确认能拦住；不能程序化的写明靠什么把关。
6. 先看它属于下面哪一类意图；属于已有的类，就挂在那一类下面，并回头检查这一类的其他地方有没有同样的问题。

**怎么用**：改界面前先读"意图总表"；检查失败时，输出里的 `lesson Lx` 指向下面对应的一条。规则的例外（比如悬停时对比度下限 4.0）只写进 `design/tokens.json`，并注明是谁、哪天同意的。

**自动检查在哪里跑**：每次编辑文件后（`.claude/settings.json` 钩子运行 `ui-check.py --hook`）；每次提交前（`.githooks/pre-commit`，新克隆的仓库先执行 `git config core.hooksPath .githooks`）；界面装进 Herdr 后（`ui-open-check.py`、`ui-shot-check.py`）。

## L1 颜色凭感觉调（I1，2026-11-25）
- **用户的意图**：界面看起来专业、经典，因为它的每个颜色都来自经过验证的公开设计系统，而不是我的审美。
- **我的思路错在哪**：觉得"调一下就好"，先动手再找依据；把设计当成可以凭感觉微调的东西。
- **这次的表现**：浅色主题我自己把颜色调深，用户说"颜色奇怪、对比度差、刺眼"；换成 Primer，最后定成 shadcn + Apple，做了三遍。
- **以后**：任何视觉数值在动手前先定来源（哪个系统、哪个令牌），从官方源码或页面数据里取，登记进 `config/themes/sources.json` / `design/tokens.json`。
- **自动检查**：C1（主题色值必须和登记的来源换算一致）、C4（mod 代码里不能新增写死的颜色）。

## L2 数值凭记忆写，规格边做边补（I1 I2，2026-11-25）
- **用户的意图**：不接受返工；看到的预览就是最终的样子。
- **我的思路错在哪**：以为记得官方的数值；以为可以边做边补规格。
- **这次的表现**：当前项指示条说成 2px，Primer 实际是 4px；右键菜单先照 Herdr 原生做，方向定下后又按 shadcn 重做。
- **以后**：先从官方源码取数值，一次把这个界面所有部件的规格写完，预览确认后再写代码（`CLAUDE.md` 规则 6）。
- **自动检查**：C9（共用菜单和对话框的常量等于 `design/tokens.json`）、C7（弹出层高度由 `menuHeight()` / `confirmHeight()` 算出）。

## L3 对比度用错了底色（I1 I6，2026-11-25）
- **用户的意图**：任何主题、任何状态下文字都看得清。
- **我的思路错在哪**：在假设的底色上手算，只算最常见的一种状态。
- **这次的表现**：space 淡底色的浓度前后算了四次（12% → 8% → 5% → 8% / 4%）：误以为侧边栏底色是面板色，漏算悬停、选中叠加后的颜色。
- **以后**：对比度永远在真实底色上算，包括叠上 `hover` / `selected` 之后，深浅两套都算。
- **自动检查**：C2（文字 ≥ 4.5，悬停 / 选中 ≥ 4.0，指示条 ≥ 3.0；淡底色行上的次要文字也算）。

## L4 规则写在文档里，但没人核对（I5 I6，2026-11-25）
- **用户的意图**：定下的规则一直有效，不会悄悄失效。
- **我的思路错在哪**：以为写进文档、自己记着就够了。
- **这次的表现**：共用件 `settings.js` 的一份副本变了样；菜单大小写混用；Windows 上叫 `Show in folder` 而不是约定的 `Reveal in File Explorer`。
- **以后**：凡是机器能判断的规则，写进文档的同时写成检查。
- **自动检查**：C5（共用件副本逐字节相同）、C6（界面字符串无中文）、C7（菜单 sentence case）、C8（图标文件存在）。

## L5 对齐靠肉眼（I2，2026-11-25）
- **用户的意图**：界面里看不见的对齐线尽可能多地对齐，整体显得安静、有秩序。
- **我的思路错在哪**：每个区块各自排版，没把整个窗口当成一张有网格的版面来算。
- **这次的表现**：侧边栏底栏和状态栏的分隔线差 12px；卡片四周的缝隙偏大，都是用户指出来的。
- **以后**：动手前算出每条横线、竖线的位置，和相邻区块对齐；对齐关系写进令牌和检查，装好后量截图。
- **自动检查**：C3（底栏同高、品牌区高度、缝隙相同、圆角相同、组头和行对齐等），S1～S3（截图里的底色、缝隙、底线）。

## L6 操作路径只有去、没有回（I4，2026-11-25，犯了三次）
- **用户的意图**：用户在界面里走到哪里都不会迷路，随时能用同样的方式回来。
- **我的思路错在哪**：只设计"前进"那一步，没有把操作路径当成一张可以往返的图。
- **这次的表现**：文件树"上一级"之后回不去；`More agents…` 把整个菜单换掉回不去；键盘把文件树固定之后只能用鼠标恢复。
- **以后**：每个"去到别处、进入另一个状态"的动作，同时设计"回来"的动作，回来的方式覆盖去的方式（鼠标对鼠标、键盘对键盘），先登记进 `design/flows.json`。
- **自动检查**：C11（每条路径的"回"覆盖"去"，登记的步骤在代码里存在）、C10（菜单不许用"弹出另一个菜单"做下一级）。

## L7 没确认真的显示出来，就说"做好了"（I6，2026-11-25）
- **用户的意图**：用户拿到的东西是能用的；不需要替我测试。
- **我的思路错在哪**：把"代码能加载、检查通过"当成完成；靠自己看截图判断有没有出现。
- **这次的表现**：加了侧向子菜单后，菜单在真实弹出层里高度为 0，截图里没有菜单我也没看出来，用户发现右键用不了。
- **以后**：装进 Herdr 后、告诉用户之前，用程序确认它真的显示、尺寸对：弹出层跑 `ui-open-check.py <mod>`，版式跑 `ui-shot-check.py`；截图只用来看样子。
- **自动检查**：`scripts/ui-open-check.py`（验证过：放回高度为 0 的版本会报 `laid out at 592x0`）。

## L8 交互不是按常识设计的（I4 I1，2026-11-26，多次）
- **用户的意图**：用户凭在其他软件里的习惯就会用，不用学。
- **我的思路错在哪**：从"技术上最省事的控件"或"上游已有的写法"出发，没先查常见软件怎么做；继承来的交互当成定稿。
- **这次的表现**：快捷键设置让人打字输入键名，而常见软件都是"按一次组合键录下来"；换掉整个菜单的子菜单。
- **以后**：任何交互先写下至少两个常见软件的做法，登记进 `design/conventions.json`，照着做；偏离要写理由；继承的交互也要补登记。
- **自动检查**：C12（每条惯例至少两个参照软件，登记的代码存在）。

## L9 改了一处设置，另一处同样的值把它盖掉了（I5 I6，2026-11-26）
- **用户的意图**：改了就生效。
- **我的思路错在哪**：没想到同一个值有两个来源；改完没验证行为真的变了。
- **这次的表现**：拖拽延迟改了 `mod.schema.json` 和常量，`main.js` 的 `DEFAULT_SETTINGS` 仍是 `400ms`，改动从没生效。
- **以后**：改任何值之前先找出它所有的来源；改完验证行为。
- **自动检查**：C13（代码默认设置和 `mod.schema.json` 一致；验证过放回 `400ms` 会被拦下）。

## L10 新原则只用在眼前，旧规则和已有文字没有回头检查（I3 I5，2026-11-26）
- **用户的意图**：界面文字克制：布局、常识、设计语言已经表达的，不再用文字说。一条原则定下来，就对所有地方有效。
- **我的思路错在哪**：觉得多写一句提示更友好；新原则只用在正在做的页面，执行旧规则时没拿新原则对照。
- **这次的表现**：按旧规则"空状态写一句话说明怎么开始"，给 Agents 空状态加了 `No agents yet. Right-click a space or use + to start one.`，说的全是界面本身已经表达的内容。用户的决定：空状态不显示文字。
- **以后**：写任何文字之前先问：布局、常识、设计语言是不是已经说明了？是就不写。定下一条新原则，就把和它矛盾的旧规则一起改掉，并列出需要按它重新检查的地方。
- **自动检查**：C14（像一整句话的界面文字，新增要用户同意并登记进 `scripts/ui-text-baseline.json`；现有 31 条从上游继承，只许减少；验证过放回那句会被拦下）。

## L11 结构没有整体设计，线索层层叠加（I2 I3，2026-11-26）
- **用户的意图**：一个结构要让人一眼看懂它要表达的几件事（这里是：在不在组里、是哪个组、组有多大），而不是一堆装饰。
- **我的思路错在哪**：一个状态一个状态往上加线索，没先问这个结构要回答哪几个问题；把临时状态（拖拽）和常态画在同一张图里。
- **这次的表现**：space 分组第一版同时用了缩进、每行组色淡底、组头色点、成员自己的颜色四种线索，再加上拖拽横线和当前项竖条。用户："又有横线又有竖线，需要做整体考虑"。用户在分区、色块、缩进树三种方案里选了色块：一块组色同时回答三个问题。
- **以后**：设计任何结构之前，先写下它要回答的问题，每个问题只配一种线索，最好一种线索回答全部；拿不准时把两三个常见做法用同一组数据并排画出来给用户选；临时状态单独画并标明。
- **自动检查**：部分程序化。C3 检查组头和行对齐（箭头在图标列、色块圆角和行相同、组间距是行距的两倍）；"每个问题一种线索"写进规格，由预览确认。

## L12 弹层的各部分各自定尺寸，留下成片的空白（I2 I3 I1，2026-11-26）
- **用户的意图**：所有弹层紧凑、和设计系统一致：它们是同一家族（菜单、确认框、选择器），用同样的内边距、格子尺寸、选中样式，不出现成片的空白。
- **我的思路错在哪**：把新组件当成一个独立的小设计，各部分（颜色行、图标格、重置按钮）各自定尺寸，间距用了自己挑的 12，而不是从已有的菜单令牌出发；也没有问每个元素是否必要（重置按钮和"无"颜色、再点一次去掉图标重复了）。
- **这次的表现**：`Appearance…` 弹层：内边距和间距都是 12；颜色行 7 个圆点加右侧重置按钮，下面图标只有 5 列，宽度不一致，右侧和中间留出整块空白；"只有图标"的那一版右上角一个重置按钮单独占一片。
- **以后**：
  - 新弹层从已有的共用件（`menu.js` 的内边距 4、格子 28、圆角 6、分隔线）出发，用同一套令牌；一个弹层里所有部分共用同一张网格（列宽、列数相同），宽度由网格决定，不留没有内容的区域。
  - 每个元素都问一遍是否必要，能用已有的元素表达的就去掉。
- **自动检查**：C3 的选择器部分（`design/tokens.json` 的 `picker`）：内边距、圆角、分隔线、格子高度和圆角必须等于菜单令牌；格子之间不留空；色点和图标一样大；需求里的图标数量必须正好填满整行（验证过：删掉一个图标会被拦下）。

## L13 把现有代码当成规格，改掉了已定的设计（I7 I2，2026-11-26）
- **用户的意图**：说定的事就是定了。要偏离，先说"这里和说好的不一样，你看怎么办"，而不是做完了才发现被改。
- **我的思路错在哪**：读到代码里单击也开 tab，就当成"现状"，把 REQUIREMENTS 里"单击 = pane、双击 = tab"那条宣布作废，再顺着现状设计了一个"预览 tab 标题斜体"来补区分。没有问：代码和文档不一致，是代码还没做到，还是文档过时了？
- **这次的表现**：P2 第一版规格作废了 §4.4 的 pane 预览，加了斜体标题；用户："单击在 pane 中，双击在 tab，已经有明显区别，不需要斜体功能了"。P4b 调研后又拿"控件放哪、默认范围"去问用户，而这两件事画板 09 和 §4.6 早就定了；用户："这些问题之前讨论过，还有对应的 claude design，能查到吗？"（2026-11-26）。
- **以后**：代码和 REQUIREMENTS 不一致时，先当成"代码没做到"，把差距列给用户，**不改文档里已确认的决定**；要新增一个机制（斜体、标记、提示）之前，先问现有的区分手段够不够。读代码得到的"现状"只用来估工作量。**问用户之前，先查 REQUIREMENTS 对应小节开头列的画板**（`docs/REQUIREMENTS.md` 第 7 行的链接），画板和文档里有答案的不问。
- **自动检查**：无（是判断，不是格式）；做法写进规则 0：开工前列出"文档说的"和"代码做的"的差距，差距里有"文档作废"的项要问用户。

## L14 新功能的界面没有先对照 Herdr 自己的同类元素（I8 I1，2026-11-26）
- **用户的意图**：能复用 Herdr 就复用 Herdr；只要是新功能扩展，界面和交互就要尽可能贴近 Herdr 的设计元素和视觉语言。代码不能复用时，复用的是它的设计系统和 UI / UX 风格。**不能有新的 pattern。**
- **我的思路错在哪**：§2.1 原则 1"贴近 Herdr 原生"早就写着，但做决定的那一刻我没有去对照：预览列的头部是新东西，我顺手用了上游 viewer 现成的文字按钮（`Preview` / `Code` / `Open in tab`），没有先问"Herdr 里和它同类的东西是什么"。答案就在旁边：预览列放在 pane 旁边，它最像的就是 pane，而 pane 的头部是图标按钮、悬停才显示、关闭是 ×。
- **这次的表现**：预览列头部第一版用了三个文字按钮加一个上游的关闭图标，"Preview"同时表示"预览列"和"渲染 Markdown"；外框用了面板的 `surface` 底，而不是旁边 pane 的外框。用户："应该模仿 pane 的 UI / UX 一样用 icon 替代，并保持紧凑"、"尽可能贴近 Herdr 原生的 pane 的表达方式和视觉语言"。
- **以后**：
  - 做任何新界面，第一步先找 **Herdr 里同类的元素**（自带 mod 在 `~/.config/herdr-app/mods/`：`pane`、`menu`、`confirm`、`tabs`、`spaces`、`files`、`peek`、`frame/*`），读它的源码，取它的尺寸、颜色令牌、出现方式（例如悬停才显示）、图标形状。能直接用它的命令或组件就直接用。
  - 代码复用不了（比如预览列是布局块，不是 pane），就复用它的样子和 pattern，并写明复用的是哪一个。
  - shadcn / Apple 只用来补 Herdr 没有定义的值；上游 mod 的组件不是来源，用之前也要对照 Herdr。
  - 回头检查同一类：已有的 14 条惯例还没写"对照 Herdr 的哪个元素"，做到相关面板时逐条补上（见下面的基线）。

## L15 在面板里加功能，只看了要加的那一块，没有对照同一个位置上已经做好的面板（I2 I5 I8，2026-11-26）
- **用户的意图**：同一个位置上的面板（Files 和 Changes 在布局里是同一个 `panel-body`，互相切换）是一家人：标题栏一样高、按钮一样大、文字从同一条竖线开始，切换时什么都不跳。已经纠正过、做好的样子，就是新功能的模板。数字会变大（1000 个改动），布局要按最长的情况设计。
- **我的思路错在哪**：只把"要加的东西"（`List | Graph`、范围下拉）当成设计对象，面板的其余部分（上游继承的标题栏、`Changes | Commits` 带框标签、计数徽标、26px 图标按钮、`Menu`）当成既定背景，往上叠；还把上游 kit 注释里的"按 Herdr 量的"当真，没有逐个对照。结果把以前纠正过的错一次全带了回来。
